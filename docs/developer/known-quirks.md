# known-quirks.md — the "looks like a bug but isn't" handbook

> Purpose: when data/artifacts "look wrong", check this table first; if the symptom is not one of these known realities, route to code via [AGENT.md](../../AGENT.md) §1.
> Related: [download.md](download.md) (mechanisms), [samples.md](samples.md) (features/labels), [data-contracts.md](data-contracts.md) (contracts and baselines), [../user/data-format.md](../user/data-format.md) (consumer view).
> The measured figures below come from the current repository artifacts (`data/organized`, `data/output`, `logs/download_full.log`).

## 1. Entries

| # | Symptom | Root cause | Fixable? | What to do |
|---|---|---|---|---|
| Q1 | A ticker's `financials.csv` financial values suddenly turn NaN for a while, then recover | **Snapshot semantics, no carry-forward across filings**: each session takes the "latest filed" row; when an 8-K/Form 4/424B*/13G and similar non-financial filing is the newest row, all concept columns are empty. Measured: after AAPL's 2009-07-28 10-Q, a Form 4 on 2009-07-29 made revenue NaN immediately, until the next 10-Q/10-K; XOM's tail is covered by SCHEDULE 13G/FWP filings | By design (conservative as-of disclosure convention; avoids treating non-financial filings as "confirmation"). Making values persist across non-financial filings means changing `organize_financials` selection logic and redefining the contract | Use `miss_*` (sample layer) or `form/quality_status` to interpret; do not treat it as a data-loss bug. Read [data-contracts.md](data-contracts.md) before changing logic |
| Q2 | XOM `revenue` is entirely empty before 2012; FY2009/10 revenue only appears in the FY2011 10-K | XOM did not tag revenue under us-gaap in early years; FY2009/10 values exist only as **comparative-period facts** in the FY2011 10-K (`filed=2012-02-24, fy=2011, end=2009-12-31/2010-12-31`). As-of extraction requires `(filed, end)` to hit the filing's own reportDate, and a comparative end does not equal that 10-K's reportDate | Fixable (e.g. place comparatives by `fy`), but it changes fiscal semantics and many historical rows — requires a contract change | Known boundary: XOM `revenue`'s first visible row = 2012-02-27 (FY2011); first-value back-checks use this as the baseline |
| Q3 | Bank `revenue`/`operating_income` almost entirely empty | The whitelist has no bank-specific tags (e.g. `InterestAndDividendIncomeOperating`). Measured: JPM has only 4 sessions with `revenue` in its full history (old `Revenues` facts from 2010–2011); the sample-layer `f_raw_revenue_yoy` has only 1 non-null row and `operating_income` is entirely empty | Fixable: add bank tags to `_CONCEPTS.revenue` (verify definitional consistency first), following the whitelist+test process in [download.md](download.md) §9 | Treat as missing/`miss_*` at training time; do not investigate JPM-like banks as "broken data" |
| Q4 | JPM's `financials_input` reaches 167,492 and organize is noticeably slower | JPM issues structured notes year after year: measured 77% of filings are 424B2 (129,203 rows), and adding FWP/424B3/424B8 and similar prospectus documents brings it to about 95%. This is the issuer shelf's real filing volume, not a duplicate-parsing bug | Not fixing (parsing de-duplicates by accession and is correct); to speed it up, pre-filter irrelevant forms in `organize_financials` and sync the contract | Treat the large filing volume as a capacity-planning input; the `(filed,end)` index + two-pointer scan exists precisely for CIKs like this |
| Q5 | Macro features are largely missing before 2000; `BAMLH0A0HYM2` only has values after 2023 | Series histories genuinely differ in length (DEXUSEU starts in 1999); the current raw response for `BAMLH0A0HYM2` has only **794 observations (from 2023-09-25)**, giving 732 non-null sessions after organize | Data-source reality, not code; rerun macros and check the FRED response count (`count` in `data/raw/fred/BAMLH0A0HYM2/*.json`) | Use `miss_m_*`; do not read it as "download failed". If a re-download still returns few rows, record it in this table |
| Q6 | Macro values appear "early" and may differ from the values published at the time | FRED is **latest revised (not vintage)**; `organize_macros` approximates the release date as "reference period + 1 month + 1 session" (FRED responses carry no release timestamp), so dates are imprecise | Not fixing (the current API cannot supply a release date); precise handling would require a vintage/ALFRED pipeline | Treat macro as "visible about a month later"; do not run release-day event studies on it |
| Q7 | 1,128 tickers have `financials.csv` but no `market.csv` | Yahoo has no market data: mostly SPAC units/warrants/preferreds/shells (155 carry suffixes such as `-UN/-WT/-P`; 973 have no hyphen in the symbol, e.g. `AACI/AACIU/AACIW`); `fetch_market` returns `None` on an empty response, and organize writes financials only | Not fixing (the securities have no Yahoo data / are delisted) | These tickers never enter samples (`build_samples` only iterates tickers with a market.csv); use `manifest.input_inventory.tickers_without_market_csv` for the list |
| Q8 | 183 tickers have `financials.csv` that is all `quality_status=missing`, and SEC requests return 404 | The Company Facts endpoint returns 404 for these CIKs (measured log: 183 unique, 279 failed retries). Mostly funds/ETFs/trusts/foreign issuers/structured products; a few US operating companies (such as OZK, PBT) are also in the list, possibly due to endpoint-side or historical XBRL gaps. **Not a CIK mismatch** (that was XOM, already fixed via override) | No code fix; optionally retry download (`--force`) later to see whether the endpoint recovers | Do not treat all-missing as an extraction bug; compare `logs/download_full.log` with the companyfacts coverage in `raw/sec/financials/manifest.json` (currently 5,883 CIKs) |
| Q9 | Multiple tickers of one issuer (share classes/warrants) have identical financial values; reverse `cik→ticker` recognizes only one | The universe lists by ticker, CIKs are per issuer; `_ticker_mappings` uses `setdefault` for `cik_to_ticker`. Measured: the 7,662 organized tickers include 892 multi-ticker CIKs; if `output_ticker` were omitted, 1,625 tickers would be written into sibling directories (e.g. `ABR-PD/ABR-PE`, or JPM/JPM-PC…/AMJB/VYLD under CIK 0000019617). Among the 183 without companyfacts, 14 are multi-ticker CIKs (18 aliases, e.g. BIOT/BIOTW, ECF/ECF-PA) | Not fixing; per-ticker artifacts are kept (manager always passes `output_ticker`) | Do not rely on the uniqueness of `_ticker_for_cik`; verify artifacts by the `organized/stocks/<TICKER>/` directory |
| Q10 | Backtests look too optimistic, and early-year universes are too small | Survivorship bias: the universe is the **current** SEC list, with no delisted tickers; 1990s cross-sections also change with the download year | Design limitation; would need historical universe snapshots | Know it explicitly when training/backtesting; see `manifest.known_biases` |
| Q11 | 364 assets in the sample have `is_common=False`; the boundary does not match intuition (hyphen-less foreign-issuer ADRs such as `HTHIF/HTHIY` are classified True) | `_is_common` is a **suffix heuristic** (`-UN/-WT/-P/-R/-U/WS/RT` plus suffixes starting/ending with those letters), not a security master; symbols without a hyphen are always True | Fixable with a security master; not fixing now | Rank/`excess_*` currently use `is_common` only to filter the benchmark; add explicit allow/deny lists if a stricter definition is needed |
| Q12 | `excess_*` benchmark returns do not match intuition | No SPY: `excess_5d/21d` subtract the **same-date equal-weight target mean of rows with `is_common=True` and `flag_extreme_label=0`**, and `is_common=False` rows also participate (their excess is measured against the common mean) | By design (equal-weight universe benchmark) | Reconstruct a cap-weighted/SPY benchmark at the training layer if needed; do not change the sample layer |
| Q13 | Label returns look unachievable (adjustment jumps, no tradable price) | `adj_open = open × adj_close / close` is an adjusted price; labels are idealized returns from the `t+1` open to the `t+1+h` open | Not fixing (the contract says so); slippage/tradability filters belong in the training layer | Do not simulate fills directly from labels; interpret them via `manifest.label_semantics` |
| Q14 | Rows with `flag_extreme_label=1` are still in the sample | Rule: when a label window crosses an adjacent-session `adjusted_open` ratio outside `[0.5, 2.0]` (unadjusted split-like price jumps), the flag is set to 1; rows are **retained, not deleted**, but excluded from `excess_*` means, and the training layer should down-weight/drop them | Fixable but should not be deleted: deleting would change row counts/split baselines | Down-weight rows with `flag_extreme_label==1` during training; currently 120,510 rows |
| Q15 | `days_since_filing` is missing about 12% of the time | Two sources: sessions before the first filing have no filing; and early organize rows with no visible filing. Measured missing rate 12.4% (coverage 87.6%), matching `miss_days_since_filing` | By design | Use `miss_days_since_filing`; do not read it as a filing-frequency feature |
| Q16 | `quality_status=missing/amendment_only` is misread as file corruption | `missing` = the latest visible filing has no whitelisted concept value; `amendment_only` = only an amendment exists, with no earlier original filing for the same report_period_end | By design | Handle by semantics: use `amendment_only` rows' financial values with care; both can be traced via `form/accession_number` |
| Q17 | Changing `preserve_progress_on_success` in `config/sources.toml` has no effect | `config.py` parses it into `SourcesConfig`, but `manager.run_download`/`progress.py` never use it; the progress file is always preserved anyway (the TOML comment says so too) | Fixable: implement the switch or remove the option | Do not use it to control reruns; use `--force` (reset progress) / `--force-rebuild` (rebuild artifacts) |
| Q18 | Re-running `--stage market` for the same range overwrites Yahoo CSVs; different ranges stack up | `fetch_market` names files `<start>_<end>.csv`; `organize_market` concatenates them and keeps the last row per date (`keep="last"`) | By design | Raw files must not be hand-edited; for an exact recompute, overwrite with the same range or clear the ticker directory before downloading |
| Q19 | A ticker's `f_raw_*_yoy` suddenly goes missing for a whole year, then recovers | `_financial_features`' fiscal main path maps `(fiscal_year, fiscal_period)` to the most recent snapshot with that key. If that snapshot carries fiscal identifiers but all four financial values are missing (whitelist had no match / empty amendment filing), the next year's YoY prior points at that empty snapshot and **does not fall back to an earlier snapshot with values** | Fixable: point the prior at the most recent snapshot with values, or skip all-empty snapshots within a key; this changes historical feature values and requires a contract change plus baseline sync | First observe the impact via `miss_*` and `qc_report.json`; if a fix is truly needed, follow the feature-change process in [AGENT.md](../../AGENT.md) §1 |

## 3. How to add or review a quirk

1. Prove the symptom with artifacts (organize CSVs, `manifest.json`, `qc_report.json`, `logs/download_full.log`), not from memory.
2. Decide whether it is "data-source reality" or a code defect: fixable and worth fixing goes through the [AGENT.md](../../AGENT.md) §1 routing and moves to §2 after the fix; unfixable stays in §1.
3. Every new entry must give: symptom, root cause (pointing at the function/file), fixable or not, and what to do; entries with numbers must state the data date (the figures here correspond to 2026-09 artifacts).
4. If an entry changes (e.g. 183 → something else, or baseline row counts move), update this table and the [data-contracts.md](data-contracts.md) baseline in the same PR.
